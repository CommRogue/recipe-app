# GCP region for Firestore, Cloud Run and Vertex AI

Research for [issue #9](https://github.com/CommRogue/recipe-app/issues/9), part of the
[v1 map](https://github.com/CommRogue/recipe-app/issues/1). Sources were read on
2026-09-16; every Google Cloud page cited below carried a "Last updated" date of
2026-09-10 to 2026-09-16. Note that the Vertex AI generative docs now live under the
name "Gemini Enterprise Agent Platform"; the old `cloud.google.com/vertex-ai/...` URLs
301-redirect to `docs.cloud.google.com/gemini-enterprise-agent-platform/...`, and the
final URLs are the ones cited here.

## Question

Which single GCP region (or Firestore multi-region) should the dev project
`recipe-app-508817` and the later prod project use, given users in the Middle East?
Firestore's location is permanent ([ADR 0001](../adr/0001-firestore-with-client-direct-access.md)),
the Go service runs on Cloud Run ([ADR 0002](../adr/0002-go-backend-on-cloud-run-for-ai-only.md)),
and recipes are generated by Gemini on Vertex AI.

## Recommendation

**Firestore and Cloud Run in `me-west1` (Tel Aviv). Gemini through the Vertex AI
`global` endpoint. Same choice in dev and prod.**

A single region for all three is not possible: no Gemini generative model is served from
any Middle East region, and the current GA Gemini 3 Flash models have no single-region
endpoints anywhere, only `global` and the `us` / `eu` multi-region endpoints. So the
region decision is really two decisions:

1. **Where the user's data and the Go service live.** `me-west1` is the only Middle East
   region on Cloud Run's Tier 1 price list (Doha and Dammam are Tier 2, 1.4x on CPU and
   memory), has the cheapest Firestore operations of the three Middle East regions
   (within 3% of Belgium), and is the closest region to users in Israel. Firestore is
   client-direct with offline sync, so its write latency is what users feel most; the
   backend only touches Firestore for Quota, and co-locating it in the same region keeps
   that path short. If the user base turns out to be mainly in the Gulf, `me-central1`
   (Doha) is the alternative at the price premium noted below.
2. **Which Vertex AI endpoint the Go service calls.** The `global` endpoint is the
   only endpoint that serves every current Gemini model, is 10% cheaper than any
   non-global endpoint for the GA Gemini 3 family, and is what Google recommends for
   availability. Its trade-off is that prompt processing can happen anywhere in the
   world; if EU-only processing is ever required, switch the location string to `eu`
   (multi-region endpoint `aiplatform.eu.rep.googleapis.com`) at a 10% price premium.
   Neither choice depends on where Cloud Run runs, because the call is server-to-server.

The Firestore multi-region `eur3` is not worth it: it doubles per-operation prices, is in
Europe anyway, and its extra availability (99.999% vs 99.99% SLO) is not something a
recipe app needs.

## The global endpoint

From [Deployments and endpoints][vai-loc]:

- "Global endpoints cover the entire world and provide higher availability and
  reliability than single regions."
- "Selecting a global endpoint for your requests can improve overall availability while
  reducing resource exhausted (429) errors. Don't use the global endpoint if you have ML
  processing requirements, because you can't control or know which region your ML
  processing requests are sent to when a request is made."
- The global endpoint is supported for every model in the table above (the page lists
  Gemini 3.8, 3.7, 3.6, 3.5 Flash, 3.5 Flash-Lite, 3.1 Flash-Lite, 3.1 Pro, 3 Flash,
  2.5 Pro, 2.5 Flash and 2.5 Flash-Lite among others).
- Capabilities not available on the global endpoint: tuning, batch prediction for
  Anthropic and OpenMaaS models, and RAG corpus (RAG requests are supported). None of
  these are in the v1 scope.
- Request URL: `https://aiplatform.googleapis.com/v1/projects/PROJECT/locations/global/publishers/google/models/MODEL:generateContent`
  (no region prefix on the host). With the Gen AI SDK the location string is `global`.
- Multi-region endpoints: `us` at `https://aiplatform.us.rep.googleapis.com` and `eu` at
  `https://aiplatform.eu.rep.googleapis.com`; the location string must be `us` or `eu`.

From [Data residency][vai-dr]:

- "Data stored at rest in the customer selected location remains at rest in that
  location, independent of the Agent Platform endpoint called by that customer's
  request." Nothing in this app stores data on Vertex AI, so this concerns Firestore and
  Cloud Run, which stay in `me-west1`.
- "Global endpoints route and process data anywhere globally, without restricting it to
  a specific geographic region ... They are designed to maximize availability and
  minimize latency by terminating TLS sessions as close to the client as possible, but
  they don't provide regional isolation or data residency guarantees."
- "The European Union multi-region (eu) endpoint strictly covers data residency within EU
  member states." The Middle East does not appear anywhere in the residency tables, so
  there is no in-region ML processing option for Middle East users at any price.

Consequence for the app: a Generation Request (Constraints, Preferences, the free-text
ask) is processed wherever Google routes it. That is a privacy-policy disclosure item
for the compliance research ticket, not a blocker.

### Firestore

- Free quota, one free (default) database per project, in any location: 1 GiB stored,
  50,000 reads, 20,000 writes and 20,000 deletes per day
  ([Firestore pricing][fs-price]).
- `me-west1` costs 13% more than `us-central1` per operation, 3% more than
  `europe-west1`, the same as `europe-west4`, 6% less than `me-central1` and 29% less
  than `me-central2`. `eur3` is 2x the `us-central1` operation price.
- SLO: regional 99.99%, multi-region 99.999% monthly uptime ([Firestore SLA][fs-sla]).
- "Be aware that once you provision a database instance, you cannot change its location
  setting." ([Firestore locations][fs-loc])

### Cloud Run

- Tier 1 regions include `me-west1`, `europe-west1`, `europe-west4`, `europe-west9`;
  Tier 2 includes `me-central1`, `me-central2`, `europe-west2`, `europe-west3`
  ([Cloud Run locations][run-loc]).
- Request-based billing, active time: Tier 1 $0.000024 per vCPU-second and $0.0000025
  per GiB-second; Tier 2 $0.0000336 and $0.0000035, so 1.4x. Idle minimum-instance time
  is $0.0000025 (Tier 1) and $0.0000035 (Tier 2). Requests are $0.40 per million in both
  tiers ([Cloud Run pricing][run-price], per-region tables).
- Free tier per billing account per month (request-based): 180,000 vCPU-seconds,
  360,000 GiB-seconds, 2 million requests, "applied as a spending based discount using
  Tier 1 pricing" ([Cloud Run pricing][run-price]).
- Cloud Run's built-in domain mapping is only offered in a short list of regions that
  does not include `me-west1` ([Cloud Run locations][run-loc]). The app talks to the
  service over its `run.app` URL, so this does not matter for v1; a custom domain later
  would go through a load balancer or Firebase Hosting rewrites.

## Setup notes for the provisioning ticket

- The default Firestore database's location is the project's immutable "location for
  default Google Cloud resources" (the App Engine location). Provisioning the default
  Firestore instance sets it, and since 2024-10-30 the default Cloud Storage for Firebase
  bucket no longer shares it ([Firebase locations][fb-loc]). So the first Firestore
  provisioning in each project must explicitly pick `me-west1`; do not accept a console
  default.
- Use the default database (`(default)`) so the free quota applies; named databases have
  no free quota ([Firestore pricing][fs-price]).
- Deploy the Go service to `me-west1` and set the Vertex AI location to `global`. Keep
  the location in configuration so it can be changed to `eu` without a code change.
- Firebase AI Logic is not in play (ADR 0002), but for the record its Vertex backend
  defaults to `us-central1` when no location is set ([Firebase locations][fb-loc]).

## What could not be verified locally

`gcloud firestore locations list` and `gcloud run regions list` both fail on
`recipe-app-508817` because the Firestore and Cloud Run Admin APIs are not yet enabled,
and this ticket did not permit enabling them. The tables above therefore rest on the
documentation only; the provisioning ticket should confirm `me-west1` appears in both
listings once the APIs are on.
